## 3. Πώς ελέγχεται σήμερα η IP μιας άδειας
`packages/nixpal-licensing/src/Zlic.php`:
1. Βρίσκει την άδεια από το κλειδί. Suspended/Expired → υπογεγραμμένη απάντηση χωρίς localkey.
2. Αν η άδεια είναι Reissued ή **δεν έχει IP**, και ο PSK είναι σωστός → **auto-bind** στην IP του καλούντα.
3. Αν η IP του καλούντα (`REMOTE_ADDR`) δεν είναι στο `License::validIps()` (το `valid_ip` χωρισμένο με κόμματα) και το
   προϊόν δεν έχει «Allow IP Conflict» → `IP Address Invalid` (χωρίς md5hash).
4. Αλλιώς υπογεγραμμένη απάντηση με `validip` = **όλο** το string, `md5hash`, `checkdate`, `localkey`.

Ήδη σήμερα μια άδεια **μπορεί** να έχει λίστα IPs (8 στις 1.339 του WHMCS). Λείπουν: ιστορικό (πότε μπήκε/βγήκε
κάθε IP, άρα τίποτα για να χρεωθεί), διαχείριση από τον πελάτη, και το auto-bind θα έδενε όποιον καλέσει πρώτος.

**Τι διαβάζουν οι clients** (`chrismfz/zonecloud`, `internal/license/check.go`, και `docs/history/blesta-modules/licensing.md`):
- Go agent: `status`, `nextduedate`, `localkey`. Του localkey ελέγχει μόνο τα δύο md5 και ότι `σήμερα (UTC) ≤ checkdate`·
  **δεν** κοιτά `validip`, `serviceid` ή `productid`. Laravel controller: `status`, `registeredname`, `nextduedate`,
  `checkdate`. C++: `status`, `localkey`.
- Ένα localkey ισχύει **μέχρι το τέλος της ημέρας UTC** που εκδόθηκε. Μετά ο agent ξαναρωτά.
- Σε `IP Address Invalid` η απάντηση δεν έχει `nextduedate`. Ο Go agent τότε γράφει `<nil>` ως αποθηκευμένη λήξη
  (`fmt.Sprintf("%v", nil)`) και επιστρέφει false. **Άρα μια IP που αφαιρείται σταματά να δουλεύει το αργότερο στο
  τέλος της ημέρας UTC.** (Το `<nil>` που σβήνει μια καλή αποθηκευμένη λήξη είναι bug του zonecloud, όχι εδώ: §10.)

Αυτό στηρίζει τη χρέωση ανά **ημέρα** (§6.1): μια IP που μπήκε για λίγες ώρες δεν «κρατά» τον agent ζωντανό για μήνα.

## 4. Μοντέλο δεδομένων

### 4.1 Προϊόν
- Το bulk είναι **ένα νέο προϊόν** στον server extension **nixpal Licensing**, με ίδιο **Secret Key (PSK)** με τον
  Zonecloud Agent (οι agents στέλνουν `ZoneCloudAgent` ως PSK και δεν αλλάζουν) και ίδιο Key Prefix `ZCAgent-`.
- **Ποια προϊόντα (υπεύθυνος, 2026-11-12):** πρώτα **Agent**. Μετά ίσως **Node (DNS)**, ως δεύτερο bulk προϊόν με τον
  δικό του PSK (`ZoneCloudNode`), prefix `ZCNode-` και δικές του κλίμακες: ίδιος κώδικας, άλλη ρύθμιση. **Όχι** Web
  Controller (λίγες άδειες, μία ανά πελάτη).
- Νέα ρύθμιση του extension **License mode**: `single` (default, ό,τι ισχύει σήμερα) | `bulk`.
- Plan μόνο μηνιαίο (§9, Ε15). Allow IP Conflict δεν επιτρέπεται σε bulk. Reissue δεν έχει νόημα σε bulk (κρύβεται).

### 4.3 Στο package
`Nixpal\Licensing\License` παίρνει ένα πεδίο `?array $ipList` (null = άδεια single, όπως σήμερα). Το
`MycsLicenseRepository::findByKey` το γεμίζει με τις ενεργές IPs όταν `mode = bulk`, και για κλειδί με
`merged_at` επιστρέφει την bulk άδεια (το κλειδί που ήρθε κρατιέται μόνο για το log). Το `WhmcsLicenseRepository`
δεν αλλάζει (το WHMCS δεν έχει bulk).

## 5. Ροή του zlic
Ο κώδικας της single άδειας **δεν αλλάζει**. Η bulk είναι ξεχωριστό κλαδί, που μπαίνει μόνο όταν `ipList !== null`:

```
findByKey(key) ─ άγνωστο ───────────────▶ Invalid (όπως σήμερα)
   │ (ψευδώνυμο → η bulk άδεια)
   ├─ Suspended/Expired ────────────────▶ υπογεγραμμένη, χωρίς localkey (όπως σήμερα)
   ├─ single ───────────────────────────▶ ο σημερινός δρόμος, αυτούσιος
   └─ bulk:
        IP ∉ ipList ────────────────────▶ {"status":"Invalid","message":"IP Address Invalid","remotecheck":true}
        (ποτέ auto-bind, ούτε σε κενή λίστα)
        IP ∈ ipList ─ λάθος PSK ────────▶ MD5 Checksum Verification Failed (όπως σήμερα)
                     σωστός PSK ────────▶ Active + md5hash + checkdate + localkey
                                           validip = η IP του καλούντα (όχι η λίστα)
                                           touch(license) + touch(license_ip)
```

- **Ίδιο JSON, ίδιο σχήμα, ίδιος αλγόριθμος** md5hash/localkey (`LocalKey`). Τα πεδία είναι τα ίδια με του verify.php.
- **`validip` = μόνο η IP του καλούντα.** Κανένας client δεν το διαβάζει (§3)· έτσι το localkey δεν μεγαλώνει με τη
  λίστα (124 IPs ≈ 2 KB σε κάθε απάντηση), και ένας server δεν μαθαίνει τις IPs των άλλων.
- **Χωρίς `validdomain`** (καμία αναζήτηση reverse DNS σε κάθε έλεγχο, όπως και στις single που είναι ήδη δεμένες)· `validdirectory` όπως σήμερα. Suspended/Expired: ίδια απάντηση με μια single, χωρίς `validip` (καμία λίστα στην απάντηση).
- **Contract:** οι υπάρχουσες άδειες δεν αγγίζονται. Τα fixtures, το `ZlicReference` oracle και το `LicensingParityTest`
  τρέχουν χωρίς αλλαγή· το PR του package προσθέτει μόνο tests για το bulk κλαδί. Μια άδεια που **συγχωνεύεται** (§8)
  απαντά πλέον με τα tags της bulk υπηρεσίας (`serviceid`, `productname`, `nextduedate`): είναι αλλαγή της άδειας, όχι
  του contract (όπως ένα upgrade στο WHMCS)· κανένας client δεν κοιτά αυτά τα πεδία πέρα από `nextduedate` (§9, Ε7).
- **Rate limit (#254):** ήδη ανά καλούντα × άδεια· ένας server που αφαιρέθηκε και επιμένει κόβει μόνο τον εαυτό του.
- **`nextduedate`** = η λήξη της bulk υπηρεσίας (πληρωμένη μέχρι), όπως σε κάθε υπηρεσία. Γι' αυτό η χρέωση μένει
  προκαταβολική (§6.2): με χρέωση εκ των υστέρων το «πληρωμένο μέχρι» θα ήταν πάντα στο παρελθόν, και μια διακοπή του
  zlic θα έριχνε όλους τους agents του πελάτη (ο Go agent πέφτει στην αποθηκευμένη λήξη όταν ο server δεν απαντά).

### 5.1 Η λίστα μετράει, όχι τα χτυπήματα
- **Πόσο συχνά καλεί κάθε IP:** ο Go agent το λιγότερο **μία φορά τη μέρα** (το localkey του ισχύει ως τα μεσάνυχτα
  UTC), και συχνότερα αν ελέγχει πιο συχνά (ο παλιός, με το bug των `\n`, ρωτούσε σε κάθε έλεγχο). Πραγματικούς
  αριθμούς ανά IP θα δώσει το `license_check_days` μετά το cut-over· το WHMCS δεν καταγράφει τις επιτυχίες.
- **Χρεώνεται η παρουσία στη λίστα**, ανά ημέρα (§6.1), είτε η IP καλεί είτε όχι. Αν χρεώναμε μόνο όσες καλούν, ένας
  server σε συντήρηση, μια διακοπή του zlic ή το rate limit θα άλλαζαν το τιμολόγιο, και θα έπρεπε να εξηγούμε γιατί
  μια μέρα δεν μέτρησε.
- **Τα χτυπήματα είναι πληροφορία:** δίπλα σε κάθε IP το τελευταίο καλό check (`last_ok_at`). Όσες δεν έχουν καλέσει
  **7 ημέρες** σημαδεύονται στον πελάτη και στην κονσόλα του staff: «τις πληρώνεις, αλλά δεν τρέχουν».
- **Καμία IP δεν αφαιρείται αυτόματα** (KISS: ενημερώνουμε, δεν αυτοματοποιούμε). Ένας server κάτω για μια εβδομάδα θα
  έχανε τη θέση του και ο agent θα σταματούσε όταν ξαναγύριζε. Μένει ώσπου να τη βγάλει ο πελάτης ή το staff.
- **Αντικατάσταση** (νέος server στη θέση παλιού): κουμπί που κάνει αφαίρεση της παλιάς και προσθήκη της νέας με το ίδιο
  label. Την ημέρα της αλλαγής μετρούν και οι δύο: μία IP-ημέρα παραπάνω (λίγα λεπτά του ευρώ), χωρίς ειδικό κανόνα.

## 6. Κανόνας χρέωσης

### 6.1 Τι μετριέται: IP-ημέρες
Μια IP μετράει για **κάθε ημερολογιακή ημέρα** (ζώνη της εφαρμογής, Europe/Athens) στην οποία ήταν ενεργή έστω και για
λίγο. Με `c_d` = ενεργές IPs την ημέρα d, `D` = ημέρες του μήνα του κύκλου, `cost(n)` = μηνιαίο κόστος n IPs με τις
κλίμακες (§6.5):

```
actual(περίοδος) = round_half_up( Σ_{d ∈ περίοδος} cost(c_d) / D , 2 )
```

- Decimal παντού (`brick/math`), **μία** στρογγυλοποίηση στο τέλος, όπως ο υπόλοιπος πυρήνας (`packages/billing-period`).
- Προσθήκη και αφαίρεση την ίδια μέρα = μία IP-ημέρα. Αλλαγή server (αφαίρεση της παλιάς, προσθήκη της νέας) την ίδια
  μέρα = δύο IP-ημέρες εκείνη τη μέρα: αμελητέο, και ποτέ λιγότερο απ' όσο δούλεψε.
- Η κλίμακα εφαρμόζεται **ανά ημέρα** στο πλήθος της ημέρας: δίκαιο και όταν ο πελάτης περνά το όριο μέσα στον μήνα.

**Γιατί όχι peak ή μέσος όρος:**
- *Peak* (το μέγιστο του μήνα): απλό, αλλά ο πελάτης που αφαιρεί στις 2 του μήνα πληρώνει όλον τον μήνα, ενώ ζητήθηκε
  «όσο αφαιρεί, κατεβαίνει». Μένει ως **ρύθμιση** (`counting: ip_days | peak`) αν το προτιμήσει ο υπεύθυνος (Ε2).
- *Μέσος όρος* (IP-ημέρες / D, μετά οι κλίμακες): σχεδόν ίδιος με τις IP-ημέρες, αλλά με κλίμακες δίνει διαφορετικό
  αποτέλεσμα από το «ανά ημέρα» και είναι δύσκολο να εξηγηθεί σε τιμολόγιο.

### 6.2 Πότε τιμολογείται: προκαταβολικά, με διόρθωση στο επόμενο
Στην ημέρα χρέωσης (κανονικό cron ανανεώσεων, `RenewalBilling`), **ένα** τιμολόγιο με:
1. **Γραμμή ανανέωσης** για τον μήνα που ξεκινά (κανονική γραμμή περιόδου, `period_start/end`, ο δρομέας του
   `billing-cursor.md` χωρίς αλλαγή): `cost(n)` με n = ενεργές IPs τη στιγμή της τιμολόγησης. Περιγραφή π.χ.
   «Zonecloud Agent Bulk License: 60 IPs (50 × 1,80 + 10 × 1,50), 01/11/2026–30/11/2026».
2. **Γραμμή διόρθωσης** για τον μήνα που έκλεισε: `actual − billed`. Νέο kind **`usage`**, **χωρίς περίοδο** (όπως το
   `KIND_CHARGE`: δεν ανανεώνει, δεν μετακινεί δρομέα)· η περίοδος που διορθώνει γράφεται στο `license_usage_periods`
   και στην περιγραφή, π.χ. «Διόρθωση χρήσης 10/2026: 2.140 IP-ημέρες, 125,32 € αντί για 105,00 € → +20,32 €».
   Μηδενική διαφορά → καμία γραμμή (η περίοδος κλείνει πάλι, με `adjustment_item_id` null).

**Αρνητική διόρθωση** (ο πελάτης αφαίρεσε IPs): αρνητική γραμμή στο ίδιο τιμολόγιο. Αν ξεπερνά τη γραμμή ανανέωσης,
το τιμολόγιο μένει 0,00 € και το υπόλοιπο γίνεται **πίστωση** στον λογαριασμό (`Credit`), ποτέ αυτόματη επιστροφή
χρημάτων (Ε5). Ο ΦΠΑ υπολογίζεται στις καθαρές γραμμές όπως σε κάθε τιμολόγιο (`LinePricer`).

**Το ποσό της ανανέωσης** βγαίνει στο `RenewalPrice::for` (ένα κλαδί για bulk), ώστε το cron, τα «Upcoming renewals»
του portal και η πρόβλεψη εσόδων (#275) να μη διαφωνούν ποτέ. Το `services.price` της bulk ενημερώνεται στην τιμολόγηση
(για τις λίστες), αλλά δεν είναι πηγή.

**Προσθήκες μέσα στον μήνα:** **δεν** βγάζουν δικό τους τιμολόγιο (αυτό είναι που φτιάχνει σήμερα τα 11 τιμολόγια τον
μήνα)· μπαίνουν στη διόρθωση του επόμενου. Για να μη μείνει ανοιχτό ρίσκο, όριο **`max_ips`** ανά υπηρεσία (ρύθμιση του
προϊόντος, με override από το staff): πάνω από αυτό ο πελάτης δεν προσθέτει χωρίς staff (Ε4).

### 6.3 Πρώτη περίοδος, ακύρωση, αναστολή
- **Παραγγελία:** ο πελάτης δηλώνει πόσες IPs (ή τις ίδιες τις IPs) στο checkout· πρώτο τιμολόγιο αναλογικό ως την ημέρα
  χρέωσης για `cost(n)`, με τους ίδιους κανόνες pro rata του προϊόντος (`Prorata`). Οι IPs ενεργοποιούνται στην πληρωμή
  (το create της άδειας, όπως σήμερα).
- **Ακύρωση στο τέλος της περιόδου:** δεν βγαίνει νέα ανανέωση· βγαίνει **τελευταίο τιμολόγιο μόνο με τη διόρθωση** της
  τελευταίας περιόδου (ή πίστωση, αν είναι αρνητική). Άμεση ακύρωση από το staff: οι IPs κλείνουν τη στιγμή της
  ακύρωσης και η διόρθωση βγαίνει αμέσως.
- **Αναστολή για απλήρωτο:** όπως κάθε υπηρεσία· όλοι οι agents του πελάτη παίρνουν Suspended. Όσο είναι σε αναστολή οι
  IPs **δεν** μετρούν (δεν δουλεύουν· ο agent πέφτει στην αποθηκευμένη λήξη, που έχει περάσει). Ε14.

### 6.4 Παραδείγματα (κλίμακες: 1–50 IPs 1,80 €, από 51 και πάνω 1,50 €, graduated)
`cost(60) = 50 × 1,80 + 10 × 1,50 = 105,00` · `cost(80) = 90,00 + 30 × 1,50 = 135,00` · `cost(40) = 72,00`

| # | Σενάριο | Υπολογισμός | Αποτέλεσμα |
|---|---|---|---|

### 6.5 Κλίμακες ως ρύθμιση
- Ανά **τιμή plan και νόμισμα** (`price_tiers`): λίστα `from_quantity → unit_price`. Η πρώτη ξεκινά από 1. Χωρίς κλίμακες,
  ισχύει η απλή τιμή του plan ανά IP.
- Ανά **προϊόν** (ρυθμίσεις του extension): `tier_mode: graduated | volume` (default graduated), `counting: ip_days | peak`
  (default ip_days), `max_ips` (default π.χ. 200), `min_monthly` (default 0,00: ελάχιστη μηνιαία χρέωση, Ε13).
- Ανά **υπηρεσία** (`service_price_tiers`, μόνο staff): για συμφωνημένες τιμές, όπως οι 0,75/1,50 € που υπάρχουν σήμερα
  με το χέρι. Ισχύει από την επόμενη περίοδο που δεν έχει κλείσει.
- Το `license_usage_periods.tiers` κρατά ό,τι ίσχυσε· μια αλλαγή κλίμακας δεν ξαναϋπολογίζει κλειστή περίοδο. Η
  ανανέωση της τρέχουσας περιόδου (ήδη τιμολογημένη με τις παλιές) διορθώνεται με τις κλίμακες που ίσχυαν στην αρχή της.
- Group discounts (`client_groups`) και ΦΠΑ: όπως σε κάθε γραμμή. Κουπόνια: όχι σε bulk στην αρχή (Ε15).

Ο υπολογισμός (κλίμακες, IP-ημέρες από διαστήματα, διόρθωση) είναι καθαρή λογική: `packages/pricing` (`Tiers` και
`UsageCharge`, PR 3), με δικά του tests, χωρίς Laravel. Με volume κλίμακες το κόστος δεν ανεβαίνει πάντα με τις IPs
(ο γκρεμός του παραδ. 7), οπότε εκεί και το *peak* μπορεί να βγει φθηνότερο από τις IP-ημέρες: ακόμα ένας λόγος για
graduated.

### 6.6 Locks
- Προσθήκη/αφαίρεση IP: υπό lock της γραμμής της άδειας (ίδιο με το `bind` σήμερα), ώστε δύο αιτήματα να μη βάλουν την
  ίδια IP δύο φορές ή να μην περάσουν το `max_ips`.
- Τιμολόγηση: υπό το lock της υπηρεσίας που ήδη παίρνει το cron· το κλείσιμο της περιόδου και η γραμμή διόρθωσης στο
  ίδιο transaction με το τιμολόγιο· το `UNIQUE(license_id, period_start)` κόβει τη δεύτερη διόρθωση.
- Tests `*Concurrency*` σε MariaDB: ταυτόχρονη προσθήκη και τιμολόγηση, δύο cron, αλλαγή από staff πάνω σε κλείσιμο.

## 8. Μετάβαση των υπαρχουσών αδειών σε μία bulk
Το δύσκολο είναι ότι **κάθε server έχει ρυθμισμένο το δικό του κλειδί**. Αν η μετάβαση ζητούσε νέο κλειδί, ο πελάτης
θα έπρεπε να αλλάξει 124 configs. Γι' αυτό τα παλιά κλειδιά γίνονται **ψευδώνυμα** της bulk (`bulk_license_id` +
`merged_at`) και συνεχίζουν να δουλεύουν· το bulk κλειδί είναι για τους νέους servers.

### 8.1 Κάθε άδεια μπαίνει στη δική της λήξη
Παράδειγμα: πελάτης με ~30 agents λέει «κάντε convert».
1. Το staff φτιάχνει την bulk υπηρεσία του πελάτη (ή υπάρχει ήδη) και, από το **Convert to bulk**, διαλέγει τις άδειες.
   Σε κάθε μία γράφεται `bulk_license_id` και η υπηρεσία της παίρνει **ακύρωση στο τέλος της περιόδου** (η κανονική
   ροή ακύρωσης, χωρίς email προς τον πελάτη).
2. **Ως τη λήξη της**, κάθε παλιά άδεια δουλεύει ακριβώς όπως σήμερα: την έχει ήδη πληρώσει.
3. **Στη λήξη της**, εκεί που θα ανανεωνόταν, η ακύρωση τερματίζει την υπηρεσία. Το `ServiceLifecycle`, για άδεια με
   `bulk_license_id`, **δεν** τη βάζει Expired: γράφει `merged_at`, και η IP της (ή οι IPs της) μπαίνει στη λίστα της
   bulk από εκείνη τη μέρα, με label το domain της παλιάς υπηρεσίας. Από εκεί και πέρα το κλειδί της απαντά ως η bulk.
4. Άδεια χωρίς IP ακόμα (δεν έχει τρέξει ποτέ): γίνεται ψευδώνυμο χωρίς IP· η προεπισκόπηση τις μετρά.

Έτσι **δεν πληρώνεται καμία μέρα δύο φορές, δεν χρειάζονται πιστώσεις ούτε αναλογικοί υπολογισμοί**, και ο πελάτης δεν
αγγίζει τους servers. Αν όλες λήγουν την ίδια μέρα (ο πελάτης με τις 124, την 1η), μπαίνουν όλες μαζί. Με διαφορετικές
λήξεις (ο πελάτης με τις 28 έχει 14), μπαίνουν σιγά σιγά μέσα σε έναν μήνα, και κάθε μία χρεώνεται στη bulk από την
ημέρα που μπήκε (§6.1).

Δύο μικροί κανόνες:
- **Η ανανέωση της bulk** μετρά και τις άδειες που μπαίνουν ως την αρχή της περιόδου που τιμολογεί, ώστε το τιμολόγιο
  που βγαίνει λίγες μέρες νωρίτερα να μην τις χάσει και να μην έρθουν όλες ως διόρθωση τον επόμενο μήνα.
- **Τιμολόγιο ανανέωσης ήδη ανοιχτό** στην παλιά (το convert έγινε αφού βγήκε): η ακύρωση στο τέλος της περιόδου το
  ακυρώνει όπως σε κάθε ακύρωση· αν έχει πληρωθεί ήδη, η παλιά μπαίνει στη bulk στην **επόμενη** λήξη της. Κανένας
  ειδικός υπολογισμός.

Η μετάβαση γίνεται **μόνο στο MyCS, μετά το cut-over**, ποτέ στο WHMCS· ο importer (L3) δεν ξανατρέχει μετά, άρα δεν
ξαναγράφει τις συγχωνευμένες. Επαναφορά: ένα ψευδώνυμο ξαναγίνεται άδεια μόνο του με νέα υπηρεσία από το staff (σπάνιο,
με το χέρι).

Το σχέδιο της 2026-11-01 (όλες μαζί σε μία ημερομηνία, με πίστωση για ό,τι πληρώθηκε πέρα από αυτή) εγκαταλείπεται:
περισσότερος κώδικας χρημάτων για ελάχιστο όφελος.

### 8.2 Η ίδια IP σε δύο άδειες
- **Τεχνικά δεν είναι conflict.** Το zlic βρίσκει την άδεια από το **κλειδί**, όχι από την IP· κάθε κλειδί ελέγχεται
  μόνο απέναντι στις δικές του IPs. Μια IP μπορεί να είναι και σε single και σε bulk, και απαντούν και οι δύο.
- Το μόνο θέμα είναι ότι ο πελάτης θα πλήρωνε δύο φορές. Άρα:
  - **ίδιος πελάτης** (π.χ. έβαλε το νέο κλειδί σε server που έχει ακόμα παλιά άδεια): **επιτρέπεται, με προειδοποίηση**
    «αυτή η IP έχει και την άδεια Χ, πληρωμένη ως 30/11· κάνε convert ή ακύρωσέ την».
  - **άλλος πελάτης**, σε bulk του ίδιου προϊόντος: **δεν επιτρέπεται**· «η IP χρησιμοποιείται ήδη, επικοινωνήστε με
    το support».
- Με τη μετάβαση του §8.1 η επικάλυψη δεν χρειάζεται καν: ο πελάτης δεν βάζει το νέο κλειδί πουθενά.
