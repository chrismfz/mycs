# Sweep: Σ1 και modules, Blesta 6.0.3 vs MyCS (2026-10-15)

Read-only σύγκριση σε 7 περιοχές (ένας agent η καθεμία): τι κάνει το Blesta 6.0.3 (`<blesta>` = ο κώδικάς του στον
orion, vendor: περιγράφεται με file:line, δεν αντιγράφεται), τι το MyCS (main μετά τα #114/#117, και το Σ1-b2 στο
branch `feat/order-status`), ετυμηγορία, αν μας αφορά κατά το WHMCS (μόνο αθροίσματα με SELECT), πρόταση. Χωρίς
αλλαγές κώδικα. Το αντίστοιχο για τη χρέωση: `docs/sweeps/billing.md` (session του billing).

## Σύνοψη: τι κάνουμε μετά (σειρά)
1. **PR ασφαλείας** (§6, **έγινε**: `fix/secrets-exposure`): DirectAdmin password καθαρό σε property (+ `str_shuffle`)· ο κωδικός του welcome mail
   καθαρός στο `email_logs` (90 μέρες)· redaction του debug log (URL/`adminapikey`, `passwd`/`rootpass`, SSO URL)·
   φόρμες server/gateway/extension που στέλνουν τα secrets στον browser· `ShouldBeEncrypted` στα mails (queue,
   `failed_jobs`).
2. **PR provisioning fixes** (§2, §4, **έγινε**: `fix/provisioning`· το change package επαληθεύτηκε σε WHM 138): cPanel change package με `changepackage` (σήμερα `modifyacct` + `plan`: πιθανό
   σιωπηλό no-op· **επιβεβαίωση σε test WHM πρώτα**· μπλοκάρει το cut-over του myip, 645 cPanel)· idempotent create
   του cPanel (username πριν το `createacct`, `accountsummary` στο retry)· `UpgradeJob` όχι σε ended υπηρεσία·
   όχι upgrade σε προϊόν άλλου module (φόρμα «Upgrades»)· `ServerSelector`: fallback στον server του προϊόντος
   χωρίς έλεγχο ορίου/enabled, groups με servers άλλου module, διαγραφή server/group που τη δείχνουν προϊόντα (§7).
3. **Importer** (§5, §7, §3): servers/groups (`tblservers`, `tblservergroups`, `tblservergroupsrel`) και server
   προϊόντος από group ή τον active server του module· οι εξαιρέσεις αναστολής ανά υπηρεσία (`overideautosuspend`,
   `overidesuspenduntil`: 14 στη nixpal) στο `suspend_hold_until`· custom fields με parity.
4. **Σ1-c custom fields προϊόντος** (§3): σχήμα και ροή εκεί· WHMCS χωρίς conditions, άρα όχι conditions.
5. Μικρά (§1, §5): πόσες απλήρωτες στο modal του Accept, μαζικό Accept· ~~email στο «Suspend server» του staff· όχι
   email «Terminated» όταν ολοκληρώνεται ακύρωση που ζήτησε ο πελάτης~~ (έγινε: «Send Notification» στο suspend, template
   `service_cancelled` στο τέλος περιόδου, κανένα δεύτερο mail στην άμεση)· `OrderDaysGrace` (myip 8, nixpal 0): τι σημαίνει το 0 στο WHMCS, πριν το cut-over.

Ανοιχτές ερωτήσεις: πουλά το myip reseller cPanel (`setresellerlimits`, §4); Τι σημαίνει `OrderDaysGrace` = 0 στο
WHMCS (§1); Τα θέματα χρέωσης στο τέλος (για τη session του billing).

## 1. Πότε στήνεται μια υπηρεσία

Σύγκριση MyCS με Blesta 6.0.3 (orion, `<blesta>`, read-only). Για το MyCS: **main** = `/root/mycs-sweep`
(Σ1-a #114 και Σ1-b1 Auto Setup #117). **b2** = `/root/mycs-b2` (`feat/order-status`: status παραγγελίας, Accept/Cancel/Refund/Fraud,
Pending Orders, `orders.invoice_id`).

  Accept είναι η καθημερινή ροή του.
- `tblorders.status`, σύνολο και τελευταίοι 12 μήνες. nixpal: Active 617/61, Cancelled 16/0, Pending 1/1, Fraud 0.
  myip: Active 6.850/459, Cancelled 196/17, Fraud 2/1, Pending 0.
- `tblhosting` Fraud: myip 2, nixpal 0.

### Σημειώσεις
- **Bug του Blesta (για αναφορά, όχι για αντιγραφή):** στο `order_orders.php:369-371` υπάρχει `$details['status'] == 'pending'`
  (σύγκριση αντί για ανάθεση), άρα το default δεν εφαρμόζεται ποτέ. Δεν μας αφορά, αλλά δείχνει ότι το status της
  παραγγελίας στο Blesta το καθορίζει μόνο το checkout.
- **Το «accepted» του Blesta δεν είναι «active».** Μην αντιστοιχιστεί έτσι, αν ποτέ γίνει import από Blesta: το Blesta βάζει
  `accepted` και σε απλήρωτες παραγγελίες.
- **Το σημαντικό υπέρ του Blesta:** το «Accept» δεν στήνει απλήρωτα. Το MyCS (b2) αποφάσισε το αντίθετο ρητά (απόφαση 2,
  2026-10-15), με δίχτυ ασφαλείας την αναστολή από το cron. Δεν προτείνεται αλλαγή. Θα βοηθούσε μια ένδειξη στο modal του
  Accept, όπως «Ν υπηρεσίες απλήρωτες», ώστε το staff να το βλέπει πριν πατήσει.
- **Προτάσεις, κατά σειρά αξίας:**
  1. (μικρό, b2 ή επόμενο) Στο modal του Accept, πόσες από τις pending υπηρεσίες είναι απλήρωτες.
  2. (μικρό) Bulk «Accept» στη λίστα Pending Orders, όπως το `updateStatus` του Blesta. Έχει νόημα στο myip, όπου 124
     προϊόντα στήνονται από το staff.
  3. (όχι τώρα) Αυτόματη εκτίμηση απάτης, υπενθυμίσεις εγκαταλελειμμένης παραγγελίας, ακύρωση από τον πελάτη: τίποτα από
     αυτά δεν υπάρχει στο WHMCS, και η χρήση του fraud είναι αμελητέα.

### Προτεινόμενο σχήμα Σ1-c (custom fields προϊόντος)

Ξεχωριστός ορισμός ανά προϊόν, τιμές στον υπάρχοντα πίνακα `properties`, ώστε να μην αλλάξει το `getServiceProperties`.

```
product_custom_fields
  id, product_id FK cascade
  key            string   (WHMCS: πριν το «|»), unique(product_id, key)
  label          string   (μετά το «|», αλλιώς ίδιο με key)
  description    string null
  type           enum: text, textarea, select, checkbox, password, link
  options        json null           (για select)
  validation     string null         (allow-list κανόνων Laravel· regex από WHMCS regexpr)
  required, admin_only, show_on_order, show_on_invoice, encrypted   bool
  sort           smallint
  whmcs_id       int null            (re-runnable importer, parity)
properties (υπάρχει) + custom_field_id → product_custom_fields (nullable), τιμή με cast encrypted όταν encrypted
```

Συμπεριφορά:
1. **Παραγγελία:** το `Checkout` προσθέτει τα `show_on_order && !admin_only` στη φόρμα και στα `rules()` (required/validation/`in:` για select)· τα περνά στο `OrderLine::$customFields`. Ο listener του `Service\Ordered` τα γράφει στο `properties` μέσα στο transaction. Ξανά έλεγχος στον server, όχι μόνο στη φόρμα (το πρόβλημα των συνθηκών του Blesta).
2. **Staff:** Create Order και Edit Service δείχνουν όλα τα πεδία (και admin-only)· τα `password`/`encrypted` εμφανίζονται κρυφά.
3. **Πελάτης:** βλέπει τα μη admin-only στη σελίδα της υπηρεσίας. Edit μόνο αν δεν έχουν ήδη τιμή (όπως το `non_editable` του `CustomProperty`) ή καθόλου, με ρύθμιση.
4. **Module:** τα πεδία φτάνουν στο `getServiceProperties()` με κλειδί `key`. Ό,τι γράφει το module (π.χ. centova/Hetzner) πάει στο ίδιο `properties` και φαίνεται στο staff αν υπάρχει ορισμός admin-only.
5. **Σύγκρουση με config option ή checkout field:** ίδια σειρά με σήμερα (checkout field → config option → CF → πεδία της υπηρεσίας), με warning στο log.
6. **Importer:** `tblcustomfields` type=product → `product_custom_fields` (fieldtype: text/textarea/dropdown/tickbox/password/link, `adminonly`, `required`, `showorder`, `showinvoice`, `regexpr`, `fieldoptions`)· `tblcustomfieldsvalues` → `properties`. Parity: πλήθος ορισμών ανά προϊόν και μη κενές τιμές ανά υπηρεσία (myip 58, nixpal 17).
7. **Licensing (nixpal):** τα 5 πεδία του `licensing` είναι τα «Custom Fields Reported» (`docs/licensing.md:18`). Το `zlic.php` πρέπει να βγάζει τα ίδια ονόματα/τιμές (byte-for-byte contract). Τα κλειδιά κρατιούνται όπως είναι στο WHMCS.

Εκτός Σ1-c (χαμηλή χρήση): συνθήκες, quantity με τιμή ανά μονάδα, «client can add» επιλογή σε υπάρχουσα υπηρεσία, module_row από επιλογή.

### Σημειώσεις
- **Το #1 είναι το μόνο ουσιαστικό εύρημα.** Τα υπόλοιπα είναι ισοδύναμα ή καλύτερα από Blesta/WHMCS. Το `modifyacct`
  ήρθε από το upstream και το `whm()` ελέγχει μόνο `metadata.result`: μια παράμετρος που αγνοείται δεν φαίνεται πουθενά.
  Ίδιος έλεγχος αξίζει για τα υπόλοιπα endpoints του CPanel extension (όλα τα υπόλοιπα, `createacct`/`suspendacct`/
  `unsuspendacct`/`removeacct`, είναι τα σωστά).
- Μετά τη διόρθωση, ένα «Change Package» θα έπρεπε να επιβεβαιώνει το αποτέλεσμα (π.χ. `accountsummary` → `plan`),
  ώστε μια σιωπηρή αποτυχία να γίνεται open action.
- Τα 23 Pending/απλήρωτα upgrades της myip (2016–2025) είναι θέμα του importer/billing, όχι του provisioning.
- Διαδικαστικό: στο orion, για να διαβάσω τα στοιχεία της βάσης του WHMCS, η εντολή επιχείρησε πρώτα `php -r` που
  κάνει include το `configuration.php` (μόνο ανάγνωση, χωρίς έξοδο προς τα έξω), πριν το fallback με grep. Στο rigel
  μόνο grep. Μόνο aggregate SELECT, κανένα δεδομένο πελάτη.

### Σημειώσεις

- **Σειρά βημάτων του cron στο MyCS:** paid_applied → credit_applied → invoices_created → orders_cancelled →
  upgrade_invoices_updated → cancellations_processed → reminders_sent → services_suspended → services_terminated.
  Είναι σωστή: πρώτα εφαρμόζονται τα χρήματα, μετά η λήξη που ζήτησε ο πελάτης, μετά το dunning. Ο κανόνας BIL-4
  εμποδίζει αναστολή και τερματισμό στο ίδιο run. Το Bl τρέχει ανεξάρτητες tasks χωρίς τέτοια εγγύηση σειράς
  (cron.php:239-241).
- **Locks:** κάθε αναστολή, τερματισμός και λήξη τρέχει σε δική της transaction με `lockForUpdate` και ξαναδιαβάζει
  τον κανόνα (CJ:256-258, 285-290, 557). Το Bl δεν κλειδώνει.
- **Pending upgrades:** τα ακυρώνει ο τερματισμός, η λήξη και το αίτημα ακύρωσης (CJ:294, 575· Listener:70-72).
  Στο Bl, μια εκκρεμής αλλαγή απλώς μπλοκάρει την αναστολή (SVC:1137-1141).
- **Κρίσιμο για το cut-over (σημείο 3):** ο importer χάνει τα «suspend until» και «never suspend» του WHMCS. Χωρίς
  αυτά, οι 14 υπηρεσίες της nixpal με hold θα ανασταλούν στο πρώτο run, αν είναι πέρα από τις 8 ημέρες. Επίσης τα
  εισαγμένα `Suspended` με «Overdue on Payment» παίρνουν `dunning_suspended_at = now()`. Άρα ο ελάχιστος χρόνος
  αναστολής μετράει από την ημέρα του import, ενώ το Termination Days μετράει από το `expires_at`, όπως πρέπει.

### Πρόταση importer (servers/groups)
1. `tblservers` → `extensions(type=server)`: `name`, `extension` από `type` (mapping WHMCS→MyCS module· άγνωστο type → enabled=false και σημείωση στο parity), `max_accounts` (0→null), `enabled = !disabled`. **Χωρίς** hostname/credentials: τα συμπληρώνει το staff ή το βήμα των κωδικών. Κλειδί re-run: mapping table `whmcs_server_id → extension_id`.
2. `tblservergroups` → `server_groups` (`filltype` 1→least_full, 2→in_order)· `tblservergroupsrel` → pivot με `position` κατά σειρά.
3. `tblproducts`: `server_group_id` από `servergroup`· `server_id` = server του group ίδιου type, αλλιώς ο `active=1` του `servertype`, αλλιώς null (+ γραμμή στο parity).
4. `tblhosting.server` → `services.server_id` αυτούσιο· ανύπαρκτος → null + parity (myip: 1 live).
5. Parity: λογαριασμοί/server (myip 657 cPanel σε 6 servers· nixpal 12), groups χωρίς server ίδιου module, live σε server άλλου module (myip: 1).

## Για την άλλη session (billing)

### Από το 1. Πότε στήνεται μια υπηρεσία
- **Ενεργοποίηση με την πληρωμή:** `RenewServiceService::activate` (`RenewServiceService.php:130-166`) είναι το ένα σημείο.
  `waitsForStaff` για τα accept/never. Με server, η υπηρεσία μένει `pending` μέχρι το CreateJob. Η περίοδος γράφεται
  κανονικά ακόμα κι αν ο server αποτύχει. Το Blesta το κάνει με cron, και μόνο όταν το τιμολόγιο είναι κλειστό
  (`date_closed`). Μερική πληρωμή δεν στήνει τίποτα, ούτε στα δύο.
- **Στήσιμο απλήρωτης** («με την παραγγελία», ή Accept του staff): `expires_at` = μέρα της παραγγελίας και «suspend hold» ως τη
  λήξη του τιμολογίου (`docs/provisioning.md` §Ημερομηνίες). Το απλήρωτο πρώτο τιμολόγιο την αναστέλλει και την τερματίζει
  όπως κάθε ληξιπρόθεσμη. Το upgrade μπλοκάρεται όσο η γραμμή της παραγγελίας είναι απλήρωτη.
- **Ανοιχτά τιμολόγια στην ακύρωση:** το Cancel/Fraud (b2) ακυρώνει μόνο τις γραμμές των υπηρεσιών στα ανοιχτά (`CancelOpenInvoices`,
  το credit επιστρέφει) και τα pending upgrades. Τα πληρωμένα μένουν. Το Blesta κάνει void όλο το τιμολόγιο της παραγγελίας,
  και πληρωμένο. **Μην το ακολουθήσουμε.**
- **Cancel & Refund** (b2): μόνο το `orders.invoice_id`. Επιστρέφει πριν ακυρωθούν τα ανοιχτά (ADV-3). Όριο το `refundable_amount`
  (ό,τι έχει ήδη γυρίσει με refund ή chargeback δεν ξαναγυρίζει). Chargeback σε περίοδο που παραδόθηκε: το τιμολόγιο ξαναχρωστιέται.
  Χρειάζεται `orders.invoice_id` σωστό από τον importer (`tblorders.invoiceid`, `ImportFromWhmcs.php:883`).
- **Ακύρωση απλήρωτης από το cron** (`orders_cancelled`): εξαιρεί τις accepted παραγγελίες (b2). Οι μερικώς πληρωμένες με
  πραγματικά χρήματα πάνε στο staff. Το credit επιστρέφει. `OrderDaysGrace`: myip 8, nixpal 0 (0 = ποτέ στο MyCS,
  `CronJob.php:165`. Χρειάζεται έλεγχος ότι το 0 του WHMCS σημαίνει το ίδιο στο cut-over).
- **Statuses:** η υπηρεσία δεν έχει `fraud` στο MyCS (γίνεται `cancelled`, και ο importer κάνει το ίδιο με τα 2 του myip). Η
  παραγγελία έχει `pending/active/cancelled/fraud`. Το `completed` των υπηρεσιών (Δ4) δεν μετράει ως «στήθηκε» στο `refreshStatus`.

### Από το 2. Το συμβόλαιο του module
1. **Το upgrade χρεώνεται πριν το εφαρμόσει ο server.** Το `ServiceUpgradeService` (`app/Services/ServiceUpgrade/ServiceUpgradeService.php:124-126`) αλλάζει προϊόν/τιμή και ξαναϋπολογίζει τις ανοιχτές γραμμές, και μετά στέλνει το `UpgradeJob`. Στο Blesta μια αποτυχία του `changeServicePackage` **ακυρώνει** την αλλαγή pricing (`services.php:2481-2500`). Σε εμάς ο πελάτης πληρώνει το νέο πλάνο ενώ ο server μένει στο παλιό, μέχρι να κλείσει η γραμμή `upgrade`. Στο downgrade παίρνει πίστωση ενώ κρατά το μεγαλύτερο πλάνο. Αυτό είναι αποδεκτό με την απόφαση 2, αλλά (α) το κουμπί Retry πρέπει να φαίνεται στη σελίδα της υπηρεσίας και (β) αν διορθωθεί το #7, ίσως υπάρχουν ήδη υπηρεσίες με πλάνο στη βάση ≠ πλάνο στον WHM, οπότε χρειάζεται ένας έλεγχος reconcile.
2. **Renew hook.** Αν προστεθεί `renewServer`, το καλεί το `RenewServiceService` `afterCommit`, μία φορά ανά πληρωμένη περίοδο. Μια αποτυχία του **δεν** αναιρεί την περίοδο· γράφεται μόνο στο `module_actions`.
3. **Το create που καθυστερεί μετακινεί τις ημερομηνίες** (`Service::datesOnStart`). Ένα create που κολλάει μέρες λόγω #6 μετατοπίζει το `expires_at` και την επόμενη τιμολόγηση. Άρα η idempotency του create έχει και οικονομική επίπτωση.
4. Το Blesta ορίζει τα retries/thresholds ανά client group. Αν κάποτε τα θέλουμε ρυθμιζόμενα, πάνε στο `docs/settings-map.md`.

### Από το 3. Επιλογές πακέτου και custom fields
- **Admin-only επιλογή που χρεώνεται:** σήμερα το `hidden` του MyCS τη βγάζει και από την τιμή (`Product.php:64` → `OrderPricing.php:46`, `Service.php:842`). Στο WHMCS μια hidden επιλογή που έβαλε το staff χρεώνεται. Ο importer πρέπει να τη φέρει χωρίς να χαθεί έσοδο (myip: 5 hidden options, 2 hidden τιμές· να μετρηθεί πόσες ενεργές υπηρεσίες τις έχουν).
- **Ανάλυση επιλογών στο τιμολόγιο:** η τιμή της επιλογής μπαίνει στην τιμή της υπηρεσίας (`Service.php:842-845`) και το τιμολόγιο έχει μία γραμμή. Το WHMCS γράφει τις επιλογές στην περιγραφή της γραμμής, το Blesta βγάζει ξεχωριστή γραμμή ανά επιλογή με `hide_on_invoice` (`ServiceItems.php:194-212`). Αφορά 213 ενεργές υπηρεσίες του myip. Πρόταση: περιγραφή «Επιλογή: Τιμή» ανά επιλογή, και ρύθμιση «χωριστή γραμμή / στην περιγραφή / καθόλου» ανά επιλογή (`config_options.invoice_display`).
- **Show on invoice για product CF:** nixpal 6/6 πεδία (licensing: IP/domain της άδειας στο τιμολόγιο). Το `Invoice::userProperties` (`Invoice.php:384-386`) καλύπτει μόνο τον πελάτη. Χρειάζεται ανά γραμμή στο `description` ή στο snapshot (`CreateInvoiceSnapshotService.php:18`), ώστε να μην αλλάζει το εκδομένο τιμολόγιο αν αλλάξει η τιμή του πεδίου.
- **Quantity με τιμή ανά μονάδα:** το `number` του MyCS δεν χρεώνεται (`OrderPricing.php:128-130`). myip: 134 ορισμοί, μόνο 1 υπηρεσία με qty>0. Να αποφασιστεί αν θα γίνει select ή αν χρειάζεται `price × qty` (decimal, tests).
- **Setup fee επιλογών:** μόνο 2 γραμμές pricing στο myip έχουν setup fee· ο `OrderPricing` το υποστηρίζει ήδη. Parity στον importer: άθροισμα τιμών επιλογών ανά ενεργή υπηρεσία = WHMCS `amount` − τιμή πακέτου.
- **Upgrade/downgrade επιλογής:** 1 στο myip (`tblupgrades` type=configoptions)· η ροή υπάρχει (SVC-6/BIL-11). Δεν χρειάζεται κάτι επιπλέον για το import.

### Από το 4. Αλλαγή πακέτου (provisioning)
- **#1 αγγίζει χρήματα έμμεσα:** με το σημερινό `modifyacct` ένα πληρωμένο upgrade cPanel μπορεί να μην εφαρμόζεται
  στον server ενώ η τιμή/τα τιμολόγια ανεβαίνουν. Μέχρι να επαληθευτεί/διορθωθεί, κανένα upgrade cPanel της myip δεν
  πρέπει να θεωρείται «παραδόθηκε» μόνο από το status του `ServiceUpgrade`.
- Blesta άμεσος τρόπος: το τιμολόγιο της αλλαγής φτιάχνεται **πριν** την κλήση του module (`client_services.php:2283-2288`)
  και σε αποτυχία του module η αλλαγή δεν γίνεται αλλά το τιμολόγιο μένει. Στο MyCS δεν ισχύει (η αλλαγή στη βάση
  γίνεται με την πληρωμή, ανεξάρτητα από τον server), απλώς για επιβεβαίωση ότι δεν το αντιγράφουμε.
- Cross-module (#6): αν κάποτε επιτραπεί, το proration/credit πρέπει να ξέρει ότι ο παλιός λογαριασμός δεν τερματίζεται
  αυτόματα. Σήμερα 0 τέτοια links.
- Upgrade σε suspended υπηρεσία (#5) εφαρμόζεται· αν η άλλη session θέλει «όχι upgrade όσο είναι suspended για χρέος»,
  είναι δική της απόφαση, το provisioning το αντέχει και στις δύο περιπτώσεις.

### Από το 5. Αναστολή, επανενεργοποίηση, τερματισμός
1. **Ανοιχτά τιμολόγια στον τερματισμό για απλήρωτο (σημείο 14):** σήμερα το `services_terminated` και το
   `Service::markTerminated()` ακυρώνουν **και** το ληξιπρόθεσμο τιμολόγιο (CJ:292-295·
   `app/Models/Service.php:454-477`). Το χρέος φεύγει από τις απαιτήσεις, οι υπενθυμίσεις σταματούν, και η αναφορά
   «οφειλέτες» μηδενίζεται. Ζητούμενα:
   (α) aggregate στο WHMCS και των δύο εταιρειών: πλήθος τιμολογίων `Unpaid` και `Cancelled` με γραμμή υπηρεσίας
   `Terminated`, για να φανεί η πρακτική ως τώρα·
   (β) ρύθμιση `cronjob_terminate_cancel_invoices` (`all` / `none` / `not_overdue_more_than:N`, όπως το
   `void_inv_canceled_service_days` του Bl), με default το αποτέλεσμα του (α)·
   (γ) tests: τερματισμός με ληξιπρόθεσμο τιμολόγιο → μένει `unpaid` και δεν ξαναζωντανεύει η υπηρεσία αν πληρωθεί
   αργότερα (το `RenewServiceService` ήδη δεν την ξαναζωντανεύει και ειδοποιεί, `:50-60`). Η πληρωμή που φτάνει τότε
   πρέπει να καταλήξει πίστωση ή refund, όχι ανανέωση.
2. **Flapping unsuspend → resuspend (σημείο 9):** πληρωμή μίας περιόδου όταν το νέο `expires_at` μένει πίσω από το
   `σήμερα − Suspend Days`. Η `activate()` (`RenewServiceService.php:129-170`) ενεργοποιεί. Το επόμενο run
   τιμολογεί (CJ:143-158) και ξαναναστέλλει (CJ:238-274), με δύο emails. Απόφαση: (α) unsuspend μόνο αν
   `newExpires >= today − cronjob_order_suspend`, αλλιώς η υπηρεσία μένει `suspended` με dunning και τιμολογείται η
   επόμενη περίοδος (εξαίρεση από το A2)· ή (β) να γραφτεί ως parity με το WHMCS. Χρειάζεται test με μηνιαία υπηρεσία
   σε αναστολή 35 ημέρες που πληρώνει ένα τιμολόγιο.
3. **A2, «η υπηρεσία σε αναστολή δεν ξανατιμολογείται» (σημείο 23):** το WHMCS τιμολογεί και τις Suspended. Στο
   cut-over, υπηρεσίες σε αναστολή μπορεί να έχουν **ήδη** πολλά απλήρωτα τιμολόγια από το WHMCS. Να ελεγχθεί ότι:
   η πληρωμή του πιο παλιού κινεί σωστά το cursor· η πληρωμή του νεότερου πρώτα περιμένει (billing-cursor)· ο
   τερματισμός τα ακυρώνει όλα σύμφωνα με το 1(β). Αξίζει parity μέτρηση: Suspended υπηρεσίες με >1 Unpaid τιμολόγιο.
4. **Importer και holds (σημείο 3):** `tblhosting.overideautosuspend` / `overidesuspenduntil` →
   `suspend_hold_until`, και «never» → ρύθμιση ή σημαία. Είναι θέμα χρέωσης, γιατί αποφασίζει ποιος θα ανασταλεί και
   θα τερματιστεί την πρώτη μέρα. Να μπει στο parity του `docs/importer.md`. Ο έλεγχος των υπενθυμίσεων
   (`app/Services/Invoice/PaymentReminders.php:204`) ήδη σέβεται το hold.
5. **Αίτημα ακύρωσης και τιμολόγια (σημείο 16):** το MyCS ακυρώνει τα ανοιχτά **τη στιγμή του αιτήματος**, όπως το
   WHMCS. Αν ο staff διαγράψει το αίτημα, το cron ξανατιμολογεί (CJ:603: χωρίς ανοιχτό τιμολόγιο και χωρίς αίτημα).
   Χρειάζεται test: «αίτημα end_of_period → τιμολόγιο ακυρώνεται → διαγραφή αιτήματος → το επόμενο run βγάζει ξανά την
   ίδια περίοδο, μία φορά, χωρίς διπλή περίοδο ή τρύπα». Επίσης test ότι η πίστωση που είχε μπει σε αυτό επέστρεψε
   ακριβώς μία φορά.
6. **Email μετά τη λήξη που ζήτησε ο πελάτης (σημείο 21):** το `endAsRequested` και το immediate στέλνουν
   «Terminated». Δεν είναι θέμα χρημάτων, αλλά αφορά τα templates της χρέωσης. Χρειάζεται ξεχωριστό template.
7. **Χειροκίνητη αναστολή χωρίς email (σημείο 7):** `EditService.php:189-192`, μικρή διόρθωση. Δεν είναι θέμα
   χρέωσης· είναι εδώ για πληρότητα.

### Από το 7. Servers, groups, επιλογή server
- Τίποτα από τους servers δεν αγγίζει ποσά· όμως: όταν ένα create αποτύχει γιατί δεν υπάρχει server με χώρο (#6), η υπηρεσία μένει πληρωμένη και pending· οι ημερομηνίες ακολουθούν το `datesOnStart` (`docs/provisioning.md`) — να μη χρεώνεται περίοδος που δεν δόθηκε.
